# Software checked low-precision binary maps

CPU admits F16, BF16, E4M3FN and E5M2 Add/Sub/Mul/Div as software integer/rational operations through the same cold prepared execution path as F32/F64. This is an explicit CPU provider implementation, not a hidden fallback or a claim of hardware half/FP8 instructions. A prepared call retains only its schema, operand mapping, operation, underflow policy and monomorphized execution pointer; it does not retain or interpret the graph during invocation.

The output format rounds to nearest, ties to even. Signed zeros remain bit exact. PCU rejects nonfinite input, overflow, zero denominator and the selected underflow fault instead of publishing IEEE default infinities/NaNs or status flags. `IeeeAfterRounding` uses destination-precision rounding with an unbounded exponent for tininess; a packed minimum-normal result alone does not establish absence of underflow. `AllowGradualUnderflow` and `RejectSubnormalResult` remain separate explicit policies. Reject-only maps preflight the whole logical extent before any output store. Faults report the lowest logical invocation; the entire output and trailing elements remain unchanged and the prepared call can retry.

The exact profile is one-dimensional, two read-only scalar loads, one checked binary instruction and one writable store, direct or grid stride, including either/both scalar broadcasts and swapped/repeated SSA operands. Cold offers are host-only, one revision-1 implementation per operation: F16 160–163, BF16 164–167, E4M3FN 168–171 and E5M2 172–175. They preserve prior IDs and report zero workspace with unknown cost. Boundary and Strict preserve the explicit checked instruction contract. PortableV1, resident boundaries, low-format Neg and low-format tensor execution are not admitted by this slice. Explicit Clamp is a separate subsequently qualified profile with its own offers and publication contract; see the sibling clamped_binary README. Exact request/IR numerical tuples are required. Backend precision and compound permissions can retain this stronger checked scalar implementation; they do not relax its explicit arithmetic instructions.

The independent control manually decodes the format, performs native binary64 arithmetic and searches adjacent destination encodings/midpoints. It calls no PCU arithmetic, conversion or packing code. The widest significands here have eleven bits. Products have at most 22 significant bits; cancellation and nearby additions fit binary64 exactly. If addition has an exponent gap too large for binary64, its small contribution cannot cross a destination midpoint or affect tiny-result classification. A division has a denominator with at most eleven bits: non-dyadic values are separated from destination midpoint and exact-result boundaries by much more than binary64's rounding error, while dyadic ties are exact. BF16's extreme products/quotients are still normal finite binary64 values, so the control does not encounter binary64 underflow/overflow or FTZ. The control assumes native round-to-nearest; production arithmetic is integer based and independent of host rounding/FTZ/DAZ.

The fixture compares all 256² operand pairs for each FP8 format, every 65,536 encoding for each half format against eleven edge partners plus one affine partner, four operations and three policies: 20,447,232 actual prepared calls. Separate tests cover direct/grid/broadcast/Strict, all six argument orders, complete schema failure, tails, faults, retry and exact cold permission rejection. The source feature adds ordinary generic `#[pcu]` calls for all four formats. Public backend admission does not extend tensor or other scalar operations.

Format authority: [OCP OFP8 revision 1.0, corrected December 2023](https://www.opencompute.org/documents/ocp-8-bit-floating-point-specification-ofp8-revision-1-0-2023-12-01-pdf-1), especially §§4–5.1. OFP8 defines interchange formats and conversions; its scope explicitly excludes arithmetic, so the binary arithmetic and checked-fault laws here are PCU's contract. [IEEE exception background](https://grouper.ieee.org/groups/msc/ANSI_IEEE-Std-754-2019/background/exceptions.txt) distinguishes exact subnormal results from default inexact-underflow behavior.
